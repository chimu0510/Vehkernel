# TOML board definitions with an MCU database and a DMA solver

The real value of ArduPilot's hwdef is its MCU database, pin validation and DMA solver, not the `.dat` format. PX4, by contrast, assembles pins by hand in `board_config.h` and fills in DMA streams and channels by hand in `timer_config.cpp`, with no conflict checking at all. Vehkernel adopts ArduPilot's toolchain but writes board definitions in TOML, the same format as parameter definitions; the board generator (`tools/generators/vkboard/`) turns them into everything else that depends on the board.

- **One pin per line**: each pin is an inline table, for example `{ pin = "PA9", role = "SERIAL2_TX", func = "USART1_TX" }`. TOML 1.0 requires inline tables on a single line, so the format itself guarantees one pin per line, ready for line-by-line comparison with the schematic. The generator catches only impossible configurations, not legal but wrong ones such as swapped encoder A/B channels, so the schematic comparison is still required.
- **The board definition is the only home of hardware facts**: pins, board devices with their mounting rotation and peripheral bus type (ADR-0015), actuator outputs and their encoders, on boards that have one, the actuator power sense input with its powered level (ADR-0005), storage devices (ADR-0019) and the Flash layout (ADR-0020). It also gives the board defaults, including the timing preset (ADR-0015), which a frame preset may override. How the board sits in a vehicle is not a fact of the board: the board orientation is a parameter (ADR-0014).
- **Actuators**: the board definition declares each actuator output by number, with its pins (for a motor driver, the PWM channel and the two direction lines) and, where the board has one, the quadrature encoder paired with it, whose two channels must be CH1 and CH2 of one timer. The numbers, not connector letters, are what parameters refer to (`MOTn_*`). The encoder resolution per wheel turn depends on the motor and gearbox, not on the board, so it is a parameter; the board definition only gives its board default for the motors the board is sold with.
- **Ports**: the board definition declares logical ports (`SERIAL1`, `SERIAL2`, ...) with their peripheral and pins, but not their use. The use is assigned at runtime by the `SERIALn_FUNCTION` parameter, for example a Link or an RC receiver, with defaults from the board defaults (like ArduPilot's `SERIALn_PROTOCOL`). On another board the same logical port may map to a different UART without any parameter change.
- **Inheritance**: `extends` and `remove`, implemented by the generator, replace hwdef's `include` / `undef`. Alt configs are written as a pin's `alt` field.
- **MCU database**: the AF table, DMA request map and Flash sector table, converted offline to JSON from the STM32Cube data through the stm32-data project and committed together with their source. Builds read only this JSON, need no network and are reproducible.
- **DMA solver**: the F4 has no DMAMUX, so each request can use only a fixed set of stream/channel pairs; the solver uses backtracking. The result must be deterministic and comes with an assignment report. USART/UART and SPI pins imply their DMA requests; other requests, such as timer or ADC requests, are listed in the board definition's `dma` array. Annotations can set a priority, disable DMA, or allow sharing; a stream is shared only when every request on it allows sharing.
- **Outputs**: typed pin constants `board.hpp`, clock configuration, DMA assignments, the peripheral instance table, the board defaults (including the timing preset, ADR-0015), Kconfig symbols such as `BOARD_HAS_*` (ADR-0017), linker script memory regions and the Flash budget (ADR-0020), and a JSON dump. The generator also checks every alt config combination for conflicts.

## Considered Options

- **A line-based format modelled on ArduPilot's `hwdef.dat`**: adopted at first, later dropped. The value lies in the toolchain behind it; a custom syntax needs a hand-written parser, while TOML inline tables give one pin per line just as well.
- **YAML board definitions**: rejected. A tree describing a flat table is verbose and hard to compare line by line with a schematic.
