# Parameter system: direct struct access, per-entry storage keyed by name hash

In RAM, parameters are plain structs that modules read directly; in Flash they are stored entry by entry, keyed by a hash of the parameter name, so changing the layout of a parameter group never invalidates user settings. This combines Betaflight's access speed, PX4's storage robustness, and the metadata of PX4 and ArduPilot.

- **Definition**: one TOML file per module or driver, giving the description, type, unit, range, default and safety attributes. It shares the board definition toolchain, whose versions are pinned by ADR-0016.
- **Access**: the generator turns each parameter group into a plain struct in RAM; modules read members directly, with no lookup. Every change publishes `parameter_update` on the bus.
- **Types**: int32 and float32 only, as in MAVLink. Booleans, enums and bitmasks are int32 and described by metadata; board definitions and frame presets give enum values by name.
- **Metadata**: the firmware holds only what validation needs: name, type, default, range and safety attributes. Descriptions, units and enum value names go into a metadata file the parameter generator writes at build time, which host tools read as they read the generated schema decoders. The handshake reports a parameter set hash, a 64-bit SHA-256 prefix over the whole metadata like the schema hash (ADR-0006); a tool whose metadata does not match warns and still works by name.
- **Access over Links**: one protocol-independent parameter service offers list, get and set, and each protocol exposes it in its own way. The custom protocol carries it as control messages, like the handshake, so its compatibility follows the protocol version (ADR-0002) and not the schema hash (ADR-0006); MAVLink maps it to its `PARAM_*` messages.
- **Storage**: entries keyed by a 32-bit FNV-1a hash of the name, storing only non-default values, each with its type and a CRC-16. The generator fails the build if any two parameter definitions in the repository share a hash, whether compiled in or not. At boot the values are filled back into the structs by hash; unknown hashes, type mismatches, out-of-range values and entries failing their CRC are skipped and reported over a Link, so no layout change ever resets user settings and a removed parameter's old value never lands in another. Flash uses two alternating 16 KB sectors with append-only writes, which survives power loss. Sector placement and the write limits while armed are in ADR-0020.
- **Default layering**, lowest first: parameter definition (which may give different defaults per vehicle type, ADR-0013) → board definition → frame preset → user value. `VEHICLE_TYPE` and `FRAME_CLASS` are resolved first (ADR-0013).
- **Safety attributes**: `reboot_required`, and `locked_when_armed` (no changes while armed).
- **Names**: at most 16 characters, upper case with a module prefix, for example `RD_WHEEL_TRACK`, for compatibility with the MAVLink parameter protocol. Each parameter definition file declares its prefix, the generator rejects a name without it, and no two files share a prefix. Every Link and ROS2 use the same name.
- **ROS2**: the MCU is the single source of truth. On connection the Bridge pulls every parameter and declares it as a ROS2 parameter from its metadata. The MCU validates each change against the range and safety attributes and returns the reason when it rejects one.

- **What becomes a parameter**: a value becomes a parameter when it differs between vehicles, motors, wiring or users, or when it is tuned, as ArduPilot and PX4 do. Values stay compile-time constants when they are fixed by a protocol or storage format (frame sizes, CRCs, the Flash layout), by a device's datasheet (register addresses, scale factors), by internal scheduling (work items per run, Flash words per run), or when they are safety invariants that no vehicle should change (the actuator power settle time, the output watchdog, which arming checks cannot be skipped). Board facts stay in the board definition and reach parameters only as board defaults (ADR-0011).
- **Later parameters**: values that are constants today but should become parameters in the milestone that first needs them:
  - `SERIALn_FUNCTION` and `SERIALn_BAUD` for every port, before the Bridge: the companion computer needs a Link on a second port, and the firmware now asserts that SERIAL1 is the Link (ArduPilot `SERIALn_PROTOCOL`, PX4 `MAV_n_CONFIG`).
  - `CTRL_RATE_HZ`, `CTRL_TRIGGER` and `IMU_SAMPLING`, `reboot_required`, with the control chain: they set the work queue periods and the IMU's sample rate divider, so they need range checks against what the board's timing can reach (ADR-0015).
  - The attitude estimator's alignment time and stillness thresholds (ADR-0014), when a vehicle aligns with motors or pumps running.
  - IMU software low-pass cutoffs, with angular rate control (PX4 `IMU_GYRO_CUTOFF`, ArduPilot `INS_GYRO_FILTER`). The sensor's full-scale ranges and on-chip filters stay fixed, as both projects keep them.
  - The failsafe action and the source timeout per mode, with the remote control and companion mode (ADR-0005; ArduPilot Rover `FS_ACTION` and `FS_TIMEOUT`, PX4 `COM_OF_LOSS_T`). Test mode keeps stop and disarm.
  - The disarmed output state, coast or brake, with the vehicle model (ArduPilot `MOT_SAFE_DISARM`).
  - Topic rates per Link, if scaling by baud rate (ADR-0002) proves too coarse (ArduPilot `SRn_*`, PX4 `MAV_n_RATE`).

## Considered Options

- **All metadata in the firmware, or PX4-style compressed metadata sent over the Link**: rejected for now. Descriptions cost Flash that only host tools need, and host tools already come from the same build.
- **Parameters as schema topics**: rejected. Parameter access is request and response with values of varying type, not publish/subscribe, and it would need topics flowing from the host onto the bus before setpoints do.
- **Betaflight's whole-block PG storage**: its storage is rejected. Any struct change bumps the version and resets the whole group to defaults. Only its direct struct access is adopted.
- **Unlimited name length, with the MAVLink protocol generating a short-name mapping**: rejected. One parameter would have two names, complicating documentation, debugging and search.
