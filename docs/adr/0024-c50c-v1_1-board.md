# The C50C V1.1: an STM32F407 robot controller with the Vehkernel bootloader on its two serial Links

The C50C V1.1 is the first board (ADR-0010). Its board definition, `boards/c50c-v1_1/board.toml`, holds its hardware facts line by line; this ADR records the facts the framework's rules leave to each board, and why the board needs what it needs. The C50C came before the rule that every board has an ADR, so this one was written after its bring-up, from the board definition and the specs that brought it up (specs 0001 to 0008).

**MCU and platform layer**

- STM32F407VET6: Cortex-M4F at 168 MHz from an 8 MHz crystal, 512 KB of single-bank Flash, 128 KB of SRAM and 64 KB of CCM. The platform layer is `platform/stm32f4/` on ST LL (ADR-0009).
- The F4 has no DMAMUX, so the board generator's backtracking DMA solver applies (ADR-0011).
- CCM can neither execute code nor be reached by DMA, so stacks and bus buffers go there and DMA buffers stay in SRAM (ADR-0008).
- Single-bank Flash stalls every fetch during an erase, so the write policy of ADR-0020 applies unrelaxed.

**Flash layout and parameter storage**

The layout is the table in ADR-0020: the bootloader in S0, parameters in S1 and S2, the event log in S3 and the firmware from S4. The C50C has no FRAM, SD card or SPI Flash, so parameters and the event log both live in internal Flash, and logs default to streaming (ADR-0019).

**Bootloader and board ID**

- The board ships with no ArduPilot or PX4 bootloader, so it gets the Vehkernel bootloader (ADR-0023), listening on SERIAL2 and then SERIAL1.
- Board ID 22083 (0x5643): in no entry of ArduPilot's `board_types.txt` and outside the range 1000 to 19999 that ArduPilot allocates, as ADR-0023 requires of a development board.
- The MCU's USB pins, PA11 and PA12, go to the USB gamepad port, so the board has no USB device to the host: no USB CDC bootloader port and no built-in USB DFU. Both serial ports reach the host through CH9102F USB serial adapters.
- SERIAL2, the one-key download port, has a DTR/RTS download circuit (RTS drives BOOT0, DTR with RTS drives NRST), so the host enters and leaves the system bootloader without touching the board. This is the board's hardware way into the system bootloader; it installs the Vehkernel bootloader on a new board and rescues a damaged one.

**Fault stop, hardware watchdog and reset cause**

How the rules of ADR-0005 land on this board:

- The motor PWM runs on TIM1 and TIM8 with OSSI set and the idle levels low, so the fault stop clears MOE on both timers, which drives every PWM pin low at once, before the outputs' own stop (no duty, direction lines low).
- The IWDG runs from the LSI, which the F407 only guarantees between 17 and 47 kHz: with a prescaler of 32 and a reload of 2047 it times out after 2.048 s at the nominal 32 kHz, 1.4 s to 3.9 s in all. The longest wait the firmware allows itself, erasing a 16 KB parameter sector, takes at most about 0.5 s. `DBGMCU_APB1_FZ` freezes it while a debugger halts the core.
- The reset cause comes from `RCC_CSR`'s reset flags, which the firmware clears at boot. The fault record is in RTC backup register 1 (a marker and the fault) and 2 (the address); register 0 holds the bootloader request (ADR-0023). The Vehkernel bootloader on this board must leave the reset flags and registers 1 and 2 alone; it may read them, as ArduPilot's bootloader boots the firmware at once after a watchdog reset.

**Revision verification at boot**

- The IMU answers as an ICM20948 (WHO_AM_I `0xEA`), and the revision-ID pins PE2, PE3 and PC13 read 0 (ADR-0010).
- The vendor firmware calls the revisions V1.0, V1.1 and V1.2; the vendor documents also use V4.0 to V4.2, and how the two naming schemes map onto each other is unconfirmed. Only V1.1, with an ICM20948, a USB gamepad and no RS-485, is on hand and defined. V1.2 moved the display's reset and data/command lines, so it would need its own board definition (ADR-0022).

**Board facts that shape the framework's defaults**

- The IMU's lines are wired the reverse of hardware I2C1, so it runs on software I2C, which bounds the IMU rate and sets the 200 Hz timing preset (ADR-0015).
- The display is on a write-only software SPI bus, so the firmware cannot tell whether it is present (ADR-0022).
- `PE4` reads the drive power circuit, a skippable arming check (ADR-0005). Its powered level is still to be measured at the hardware check of spec 0006.

## Consequences

- The board definition is written from the schematic, the vendor firmware and bench measurements, never from the vendor resource allocation table: the table lists PC13, PE2 and PE3 as unused although they are the revision-ID pins, and its display pins do not reflect the V1.2 change.
- Vendor firmware differs from board to board, so each board's backup stays outside the repository.
